# Wewire 法币链路测试方案

## 1. 角色与链路

本次测试涉及 3 个角色：

- 法币渠道：`Wewire`
- Pay：`PAY`
- RB：`RB（我们）`

链路关系：

`Wewire -> PAY -> RB`

说明：

- `Wewire` 提供 `VA`、`EUR 开户`、`入金`、`回调`能力。
- `PAY` 是 `RB` 的上游，负责渠道路由、通道权限控制、订单承接、回调转发、下发 API。
- `RB` 负责发起请求、下单、接收回调、入账、对账。

## 2. 测试目标

验证以下能力完整可用且数据一致：

1. `RB` 调用 `PAY` 完成 `VA` 流程。
2. `RB` 调用 `PAY` 完成 `EUR 开户`。
3. `RB` 调用 `PAY` 完成 `入金`。
4. `RB` 能收到并正确处理 `PAY`/`Wewire` 回调。
5. `PAY` 后台路由配置、`RB` 路由配置正确生效。
6. `RB` 下单后，`PAY` 后台可生成对应订单且状态流转正常。
7. `PAY` 对 `RB` 的通道权限控制生效。
8. `PAY` 下发 API 能正常调用，且权限、参数、状态返回正确。
9. `RB` 与 `PAY`、`PAY` 与 `Wewire`、`RB` 内部账务三方可对账。

## 3. 建议先确认的信息

执行前建议补齐以下信息，否则很多用例只能做半验证：

- `RB -> PAY` 的接口文档、签名方式、鉴权字段。
- `PAY -> RB` 回调文档：回调地址、字段、签名、重试机制、幂等要求。
- `Wewire` 能提供的环境：测试环境/生产环境。
- `VA`、`EUR 开户`、`入金`、`下发` 各接口的状态枚举。
- `PAY` 后台路由配置维度：按商户、币种、国家、产品、通道、优先级还是开关。
- `RB` 路由配置维度与生效规则。
- 对账口径：订单维度、资金维度、余额维度；对账周期 T0/T1。
- 是否有人工补单、人工改状态、手工重推回调能力。

## 5. 端到端核心测试点

## 5.1 VA / 开户

- `RB` 发起创建 `VA`/开户请求，请求参数合法时返回成功。
- `PAY` 接到请求后命中正确路由，落到 `Wewire`。
- `PAY` 后台生成订单，且订单号、商户号、用户标识、币种、金额等与 `RB` 请求一致。
- `Wewire` 返回成功后，`PAY` 正确更新订单状态并同步给 `RB`。
- `RB` 能保存返回的 `VA` 信息、开户信息。
- 回调到达 `RB` 时字段完整、签名正确、状态正确。
- `RB` 对回调做幂等处理，重复回调不重复开户、不重复记账。

## 5.2 入金

- 使用已成功开户/已成功生成 `VA` 的账户做入金。
- `Wewire` 入金后，`PAY` 能接收上游结果并生成或更新对应订单。
- `RB` 能通过回调或主动查询拿到入金成功结果。
- `RB` 入账金额、手续费、净额、币种与上游一致。
- 多笔入金时，能正确区分不同订单与不同 `VA`。
- 部分失败、处理中、成功等状态能正确流转。

## 5.3 对账

- `RB` 订单数与 `PAY` 订单数一致。
- `PAY` 订单数与 `Wewire` 订单数一致。
- 成功金额、失败金额、处理中金额分别一致。
- 手续费、净额、汇总金额一致。
- 回调成功但 `RB` 未入账、已入账但 `PAY` 未成功等差异单可识别。
- 对账文件或对账接口中的时间范围、时区、币种过滤正确。

## 5.4 路由配置

- `PAY` 路由配置为 `Wewire` 后，`RB` 下单命中 `Wewire`。
- `PAY` 关闭 `Wewire` 通道后，`RB` 下单失败或切到备用通道，行为符合设计。
- `RB` 自身路由切换后，订单按预期走到目标 `PAY` 路由。
- 多条路由规则同时存在时，优先级正确。
- 路由配置变更后，是否即时生效符合预期。
- 配置只影响新订单，不影响已生成订单。

## 5.5 权限控制

- `PAY` 允许 `RB` 走 `Wewire` 时，下单成功。
- `PAY` 不允许 `RB` 走某通道时，下单应明确失败，错误码清晰。
- `RB` 没有某币种或产品权限时，不应绕过限制成功下单。
- 下发 API 仅允许有权限的 `RB`/商户调用。
- 同一个 `RB` 下不同商户号权限不同的场景要覆盖。

## 5.6 回调

- 成功回调：`RB` 收到后状态更新成功。
- 失败回调：`RB` 能更新失败原因并支持后续重试或人工处理。
- 重复回调：`RB` 只处理一次，返回固定成功响应。
- 无效签名回调：`RB` 拒绝处理并记录日志。
- 回调乱序：先收到成功再收到处理中，或先失败后成功，状态机处理正确。
- 回调超时/`RB` 返回非 200：`PAY` 是否按规则重推。

## 5.7 下发 API

- 正常参数调用成功。
- 缺字段、错字段、非法金额、非法币种时正确报错。
- 无权限商户调用被拦截。
- 重复请求具备幂等能力。
- 订单状态、余额变化、回调逻辑与设计一致。

## 7. 异常与边界场景

- 同一业务单号重复提交。
- 同一请求在网络超时后重试。
- `PAY` 已落单但 `RB` 未收到响应。
- `Wewire` 成功但 `PAY` 回调给 `RB` 失败。
- 回调延迟很久才到。
- 金额为最小值、最大值、边界值。
- 币种不支持。
- 账户已冻结/已关闭后继续入金。
- 路由配置刚修改时并发下单。
- `PAY` 后台手工改状态后是否会影响 `RB`。

## 8. 执行建议

建议按以下顺序执行，能更快定位问题：

1. 先测配置与权限：确认 `RB` 是否有权走 `Wewire`。
2. 再测 `VA` 和 `EUR 开户`：确认基础账户能力通。
3. 再测入金链路：确认订单、状态、回调完整闭环。
4. 再测下发 API：确认反向资金能力。
5. 最后做对账和异常回归：确认稳定性与账务一致性。

## 10. 当前方案的假设

本方案基于以下假设整理：

- `RB` 是调用方，`PAY` 是上游聚合层，`Wewire` 是实际法币渠道。
- `Wewire` 已提供 `VA`、`EUR 开户`、`入金`、`回调`能力。
- `PAY` 具备后台路由配置、权限控制、订单管理和下发 API。
- `RB` 需要同时验证接口、后台订单、回调和对账闭环。
