# Wewire - PAY - RB 详细测试用例

## 1. 测试对象

- 法币渠道：`Wewire`
- 上游聚合：`PAY`
- 我方系统：`RB`

链路：

`Wewire -> PAY -> RB`

## 2. 执行前统一前置条件

除特殊说明外，默认前置条件如下：

1. `RB`、`PAY`、`Wewire` 均有可用测试环境。
2. `RB -> PAY` 接口联调完成，鉴权、签名已配置正确。
3. `PAY -> RB` 回调地址已配置，`RB` 可正常接收回调。
4. `PAY` 后台已开通 `Wewire` 通道。
5. 测试商户、测试用户、测试币种 `EUR` 已准备。
6. 可查看 `PAY` 后台订单、路由配置、权限配置。
7. 可获取 `RB` 侧订单、账务、回调处理日志。
8. 如需验证 `Wewire` 侧结果，已具备查询方式或渠道侧配合人。

## 3. 详细测试用例

## 3.1 路由配置

### TC-ROUTE-001 `PAY` 路由命中 `Wewire`

- 前置条件：
  `PAY` 后台已配置 `RB` 商户的 `EUR` 开户/入金路由至 `Wewire`，且规则已启用。
- 测试步骤：
  1. 在 `RB` 发起一笔 `EUR` 开户或 `VA` 创建请求。
  2. 记录 `RB` 请求单号、请求时间、请求参数。
  3. 登录 `PAY` 后台查询对应订单。
  4. 查看订单命中的通道信息和路由信息。
- 预期结果：
  1. `RB` 请求被 `PAY` 正常受理。
  2. `PAY` 后台生成对应订单。
  3. 订单命中通道为 `Wewire`。
  4. 路由规则、商户号、币种与配置一致。

### TC-ROUTE-002 `PAY` 关闭 `Wewire` 后下单

- 前置条件：
  `PAY` 已关闭 `Wewire` 通道，或将 `RB` 到 `Wewire` 的路由规则禁用。
- 测试步骤：
  1. 在 `RB` 发起一笔原本应走 `Wewire` 的请求。
  2. 查看 `RB` 返回结果。
  3. 查看 `PAY` 是否生成订单，及路由去向。
- 预期结果：
  1. 若无备用通道，请求应失败，错误原因明确。
  2. 若配置了备用通道，请求应切换到备用通道。
  3. 不应继续命中被关闭的 `Wewire`。

### TC-ROUTE-003 `RB` 路由切换生效

- 前置条件：
  `RB` 存在可切换的路由配置项，且可以指定对接的 `PAY` 路由策略或产品。
- 测试步骤：
  1. 在 `RB` 将目标业务的路由切换到指定策略。
  2. 发起一笔订单。
  3. 在 `PAY` 后台查看订单的路由落点。
- 预期结果：
  1. `RB` 路由修改后，新订单按新规则发出。
  2. `PAY` 接收到的新订单与新路由配置匹配。
  3. 历史订单不受影响。

### TC-ROUTE-004 多路由优先级验证

- 前置条件：
  `PAY` 中存在多条可同时命中的路由规则，且规则优先级不同。
- 测试步骤：
  1. 配置两条以上满足相同业务范围的规则。
  2. 发起一笔符合多条规则的订单。
  3. 查看实际命中规则。
- 预期结果：
  1. 实际命中最高优先级规则。
  2. 命中结果与后台配置一致。
  3. 不出现随机落路由的情况。

## 3.2 权限控制

### TC-AUTH-001 `RB` 有权限时可走 `Wewire`

- 前置条件：
  `PAY` 已给 `RB` 商户开通 `Wewire` 通道权限。
- 测试步骤：
  1. 在 `RB` 发起一笔 `Wewire` 相关业务请求。
  2. 查询 `RB` 返回和 `PAY` 后台订单。
- 预期结果：
  1. 请求成功受理。
  2. `PAY` 后台正常生成订单。
  3. 订单流向 `Wewire`。

### TC-AUTH-002 `RB` 无权限时禁止走 `Wewire`

- 前置条件：
  `PAY` 已移除 `RB` 对 `Wewire` 的通道权限。
- 测试步骤：
  1. 在 `RB` 再次发起相同请求。
  2. 记录返回结果。
  3. 查看 `PAY` 后台是否有对应订单。
- 预期结果：
  1. 请求被拒绝，返回权限不足或通道不可用。
  2. 不应错误地下发到 `Wewire`。
  3. 若生成订单，也应为失败订单且失败原因准确。

### TC-AUTH-003 币种权限校验

- 前置条件：
  `RB` 仅有 `EUR` 权限，无其他币种权限。
- 测试步骤：
  1. 先发起一笔 `EUR` 请求。
  2. 再发起一笔无权限币种请求。
- 预期结果：
  1. `EUR` 请求可正常处理。
  2. 无权限币种请求被拒绝。
  3. 报错信息能反映币种权限问题。

## 3.3 VA / EUR 开户

### TC-ACC-001 成功创建 `VA`

- 前置条件：
  `RB` 已具备 `Wewire` 通道和 `EUR` 业务权限，请求参数符合接口要求。
- 测试步骤：
  1. 在 `RB` 发起创建 `VA` 请求。
  2. 记录请求报文、商户号、用户号、业务单号。
  3. 查看 `RB` 返回结果。
  4. 在 `PAY` 后台查询订单。
  5. 核对是否收到成功回调。
- 预期结果：
  1. `RB` 接口返回成功或受理成功。
  2. `PAY` 后台生成对应订单。
  3. 订单字段与 `RB` 请求一致。
  4. `Wewire` 返回成功后，`PAY` 状态更新为成功。
  5. `RB` 收到成功回调并保存 `VA` 信息。

### TC-ACC-002 成功完成 `EUR` 开户

- 前置条件：
  已准备真实可用的开户必填字段，如用户身份、国家、姓名、地址等。
- 测试步骤：
  1. 在 `RB` 发起 `EUR` 开户请求。
  2. 记录开户参数和业务单号。
  3. 查看接口返回。
  4. 在 `PAY` 后台确认订单创建情况。
  5. 等待并检查回调结果。
- 预期结果：
  1. 开户请求成功受理。
  2. `PAY` 后台生成开户订单。
  3. 开户成功后，`RB` 能获得开户结果和账户信息。
  4. 订单状态、回调状态、`RB` 最终状态一致。

### TC-ACC-003 开户缺少必填字段

- 前置条件：
  选择一个接口必填字段，例如姓名、证件号、国家或币种。
- 测试步骤：
  1. 发起一笔缺少必填字段的开户请求。
  2. 查看接口返回。
  3. 查看 `PAY` 后台是否生成订单。
- 预期结果：
  1. 请求被拦截或校验失败。
  2. 返回缺字段或参数非法错误。
  3. 不应生成成功订单。
  4. 如生成失败订单，失败原因明确且不进入正常流转。

### TC-ACC-004 重复业务单号开户

- 前置条件：
  已有一笔成功或受理中的开户请求业务单号。
- 测试步骤：
  1. 使用相同业务单号重复提交开户请求。
  2. 比较两次返回结果。
  3. 查看 `PAY` 后台订单数量。
- 预期结果：
  1. 系统具备幂等处理。
  2. 不重复创建多笔有效订单。
  3. 返回结果与幂等设计一致。

## 3.4 入金

### TC-DEP-001 入金成功

- 前置条件：
  已成功创建 `VA` 或已完成 `EUR` 开户，可触发渠道侧入金。
- 测试步骤：
  1. 向该账户发起一笔测试入金。
  2. 记录金额、币种、时间、渠道流水号。
  3. 查看 `PAY` 后台订单状态变化。
  4. 检查 `RB` 是否收到回调或主动查询到结果。
  5. 核对 `RB` 入账金额。
- 预期结果：
  1. `PAY` 能接收到 `Wewire` 入金结果。
  2. `PAY` 后台生成或更新入金订单。
  3. `RB` 收到成功结果并完成入账。
  4. 金额、币种、订单状态一致。

### TC-DEP-002 入金处理中后成功

- 前置条件：
  渠道支持先返回处理中，再返回成功。
- 测试步骤：
  1. 发起一笔会经历处理中状态的入金。
  2. 观察 `PAY` 与 `RB` 状态流转。
  3. 记录处理中到成功的变化时间。
- 预期结果：
  1. 状态先进入处理中。
  2. 后续收到成功通知后正常更新为成功。
  3. `RB` 最终只入账一次。

### TC-DEP-003 入金失败

- 前置条件：
  准备一笔可触发失败的测试条件，如无效账户或渠道模拟失败。
- 测试步骤：
  1. 发起入金。
  2. 观察 `RB`、`PAY`、`Wewire` 的返回或回调。
  3. 查看失败原因记录。
- 预期结果：
  1. 订单最终状态为失败。
  2. 失败原因在 `RB` 和 `PAY` 侧可追踪。
  3. 不发生错误入账。

### TC-DEP-004 同一账户多笔入金

- 前置条件：
  已有一个可正常入金的 `VA`/账户。
- 测试步骤：
  1. 连续发起 2 到 3 笔不同金额的入金。
  2. 分别记录每笔流水。
  3. 查看 `PAY` 与 `RB` 的订单记录和账务记录。
- 预期结果：
  1. 每笔入金都对应独立订单或独立记录。
  2. 不串单、不覆盖、不丢单。
  3. 每笔金额都准确入账。

## 3.5 回调

### TC-CB-001 成功回调正常处理

- 前置条件：
  `RB` 已配置正确回调地址，且可查看回调处理日志。
- 测试步骤：
  1. 完成一笔成功业务。
  2. 等待 `PAY` 回调到 `RB`。
  3. 查看 `RB` 回调接收日志和订单状态。
- 预期结果：
  1. `RB` 成功接收回调。
  2. 回调签名校验通过。
  3. `RB` 订单状态更新为成功。
  4. 返回 `PAY` 的响应符合约定。

### TC-CB-002 重复回调幂等

- 前置条件：
  可让 `PAY` 对同一笔订单重复推送回调，或支持手工重推。
- 测试步骤：
  1. 对同一笔成功订单连续推送 2 到 3 次相同回调。
  2. 查看 `RB` 回调处理记录。
  3. 检查账务是否重复入账。
- 预期结果：
  1. `RB` 对相同回调只做一次有效处理。
  2. 不重复记账、不重复更新关键业务结果。
  3. 重复回调仍返回约定成功响应。

### TC-CB-003 回调签名错误

- 前置条件：
  支持构造错误签名回调，或可在测试环境模拟。
- 测试步骤：
  1. 向 `RB` 推送一笔签名错误的回调。
  2. 查看 `RB` 接口响应与日志。
- 预期结果：
  1. `RB` 拒绝该回调。
  2. 订单状态不被错误更新。
  3. 日志中明确记录签名错误原因。

### TC-CB-004 回调乱序

- 前置条件：
  支持模拟先成功后处理中，或先失败后成功的乱序通知。
- 测试步骤：
  1. 先推送高优先级最终状态回调。
  2. 再推送低优先级中间状态回调。
  3. 查看 `RB` 最终订单状态。
- 预期结果：
  1. `RB` 状态机按设计处理乱序通知。
  2. 最终状态不被旧状态覆盖。
  3. 日志中可定位乱序事件。

### TC-CB-005 回调失败后的重试

- 前置条件：
  支持模拟 `RB` 首次回调响应超时或非 200。
- 测试步骤：
  1. 让 `RB` 第一次回调处理返回失败。
  2. 观察 `PAY` 是否进行重推。
  3. 第二次恢复正常处理。
- 预期结果：
  1. `PAY` 按既定机制重试回调。
  2. `RB` 在成功接收后完成正确更新。
  3. 最终只形成一次有效业务结果。

## 3.6 订单与数据一致性

### TC-ORD-001 `RB` 下单后 `PAY` 生成对应订单

- 前置条件：
  `RB` 与 `PAY` 接口通畅。
- 测试步骤：
  1. 在 `RB` 发起一笔订单。
  2. 记录 `RB` 业务单号。
  3. 在 `PAY` 后台按业务单号查询。
  4. 核对字段。
- 预期结果：
  1. `PAY` 后台存在对应订单。
  2. 商户号、用户号、金额、币种、产品类型一致。
  3. 创建时间与请求时间基本匹配。

### TC-ORD-002 `RB` 超时但 `PAY` 已落单

- 前置条件：
  可模拟 `RB` 请求超时或网络中断。
- 测试步骤：
  1. 发起一笔请求，并在响应阶段制造超时。
  2. 查看 `RB` 侧返回。
  3. 到 `PAY` 后台查询是否已落单。
  4. 再次使用相同业务单号重试。
- 预期结果：
  1. 即使 `RB` 未及时收到响应，`PAY` 已落单时应可查询到该订单。
  2. 重试请求遵循幂等规则。
  3. 不产生重复有效订单。

## 3.7 下发 API

### TC-PAYOUT-001 有权限商户调用下发 API 成功

- 前置条件：
  `RB` 商户具备下发 API 权限和足够余额。
- 测试步骤：
  1. 在 `RB` 发起一笔下发请求。
  2. 查看接口返回。
  3. 在 `PAY` 后台查询订单。
  4. 检查回调和状态变化。
- 预期结果：
  1. 下发请求成功受理。
  2. `PAY` 后台生成下发订单。
  3. 状态流转、回调结果与设计一致。

### TC-PAYOUT-002 无权限商户调用下发 API

- 前置条件：
  测试商户未开通下发 API 权限。
- 测试步骤：
  1. 发起一笔下发请求。
  2. 查看返回结果和后台记录。
- 预期结果：
  1. 请求被拒绝。
  2. 报错信息明确体现权限问题。
  3. 不应成功进入正常下发流程。

### TC-PAYOUT-003 下发请求参数非法

- 前置条件：
  准备非法金额、非法币种、缺失收款方字段等异常参数。
- 测试步骤：
  1. 分别发起多组非法参数请求。
  2. 记录每组返回结果。
- 预期结果：
  1. 每组异常参数都被正确拦截。
  2. 返回错误信息准确。
  3. 不生成脏数据或异常成功订单。

### TC-PAYOUT-004 下发重复请求幂等

- 前置条件：
  已有一笔成功受理的下发业务单号。
- 测试步骤：
  1. 使用相同业务单号重复请求。
  2. 查询 `PAY` 后台订单情况。
- 预期结果：
  1. 不重复生成多笔有效订单。
  2. 返回结果符合幂等设计。

## 3.8 对账

### TC-REC-001 `RB` 与 `PAY` 按日对账一致

- 前置条件：
  当日已产生多笔成功、失败、处理中订单。
- 测试步骤：
  1. 导出或查询 `RB` 当日订单数据。
  2. 导出或查询 `PAY` 当日订单数据。
  3. 按订单号、金额、状态逐笔比对。
- 预期结果：
  1. 订单笔数一致。
  2. 成功金额、失败金额、处理中金额一致。
  3. 手续费、净额口径一致。

### TC-REC-002 `PAY` 与 `Wewire` 对账一致

- 前置条件：
  能获取 `Wewire` 订单明细或对账文件。
- 测试步骤：
  1. 拉取 `PAY` 当日对应通道订单。
  2. 获取 `Wewire` 对账明细。
  3. 核对订单号映射、金额、状态。
- 预期结果：
  1. `PAY` 与 `Wewire` 数据一致。
  2. 若存在差异单，可定位是订单未同步、状态未更新还是回调未处理。

### TC-REC-003 差异单识别

- 前置条件：
  人为构造一笔 `PAY` 成功但 `RB` 未入账，或 `RB` 入账但状态未更新的数据。
- 测试步骤：
  1. 运行对账。
  2. 检查差异单报表或差异识别逻辑。
- 预期结果：
  1. 差异订单可被识别出来。
  2. 差异类型可区分为状态差异、金额差异、缺单差异等。
  3. 支持后续人工排查。

### TC-REC-004 时间范围与时区校验

- 前置条件：
  在临近跨日时间点准备订单数据。
- 测试步骤：
  1. 使用不同时间范围查询或导出对账数据。
  2. 比较 `RB`、`PAY`、`Wewire` 统计口径。
- 预期结果：
  1. 跨日订单归属正确。
  2. 时区换算无偏差。
  3. 不发生漏单或重复统计。
